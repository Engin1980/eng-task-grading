# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

Monorepo for a teacher-facing course/task/grade/attendance app (UI text and some docs are in Czech):

- `EngTaskGradingNetBESolution/` — .NET 8 ASP.NET Core Web API (`EngTaskGradingNetBE/`), EF Core + SQL Server, Serilog, JWT auth.
- `eng-task-grading-react-fe/` — React 19 + TypeScript + Vite SPA (TanStack Router/Query/Form, Tailwind 4, axios).
- `docker-release/` — production compose (`docker-compose.example.yml`, `.env.example`) that builds both FE and BE plus the DB. Copy the example and fill in the `TODO` secrets.

There is no automated test project and no CI workflow (`.github/workflows` is empty).
`docker-release/.env` is untracked/local; don't commit it.

## Commands

Frontend (run in `eng-task-grading-react-fe/`):
- `npm install`, `npm run dev` (Vite over HTTPS — requires `certs/localhost-key.pem` and `certs/localhost.pem`, see `vite.config.ts`), `npm run build` (`tsc -b && vite build`), `npm run lint`.
- `src/routeTree.gen.ts` is generated by the TanStack router plugin — don't edit by hand; add route files under `src/routes/`.
- App version is taken from `package.json` `version` (exposed as `VITE_APP_VERSION`); bump it on releases.

Backend (run in `EngTaskGradingNetBESolution/`):
- `dotnet build EngTaskGradingNetBE.sln`, `dotnet run --project EngTaskGradingNetBE`.
- Local stack: `docker compose up -d` (SQL Server + BE; the base `docker-compose.yml` is for dev, with `docker-compose.override.yml` on top).
- Release: see `how-to-release.md` (self-signed pfx cert per `certs/readme.md`, `docker-compose.release.yml` override, `appsettings.release.json`).
- EF migrations live in the BE project and are applied automatically on startup.

## Backend architecture

- `Program.cs` wires everything through `Build*` local functions: logging, services, JWT security, CORS, DB. Order in the pipeline matters (`GlobalExceptionHandler` first, CORS before auth).
- **DB password** is not in appsettings: the connection string contains a `{DB_PASSWORD}` placeholder replaced from the `DB_PASSWORD` env var at startup. The app throws if the env var, JWT secret (`AppSettings:Security:AccessTokenJwtSecretKey`) or `AppSettings:FrontEndUrl` is missing. Config is overridden through env vars with `__` separators (e.g. `AppSettings__Emails__Configs__Osu__SenderEmail`).
- **Logging** is two-phase: console/file first, then after `db.Database.Migrate()` the logger is rebuilt with an MSSQL `AppLog` sink (surfaced through `AppLogController`).
- Layering: `Controllers/` → `Services/` (all registered transient in `Program.cs`) → `Models/DbModel` (EF entities, `AppDbContext`); `Models/Dtos` for API shapes; `Lib/EObjectMapper` for mapping. `AuthController` is split into partial files (`+Teacher`, `+Student`, `+Generic`, …).
- Errors: throw typed exceptions from `Exceptions/` (`BadData/*` → client errors, `Server/*` → server errors); `Middleware/GlobalExceptionHandler` converts them to responses.
- Background work: `BackgroundTaskQueue` + `BackgroundTaskManagerService` (e.g. emails), and `DatabaseBackupHostedService`.
- Optional Cloudflare Turnstile verification (`CloudflareTurnistilleService`), toggled by config.
- Two auth audiences: teachers (JWT login/register) and students (self-sign attendance keys / student view).
- `Controllers/_Endpoints.md` is an (outdated, Czech) endpoint overview; routes are mostly `api/[controller]`, with `api/v1/teacher` and `api/v1/applog` as exceptions. `.bruno/` holds Bruno API request collections.

## Frontend architecture

- File-based routing in `src/routes/` (teacher area: `courses/`, `attendances/`, `attendanceDays/`, `admin/`; student area: `studentView/`, `attendanceSelfSign/`).
- `src/config/app-settings.ts` reads config from runtime `window.__APP_CONFIG__` first, then build-time `import.meta.env.VITE_*`. The FE Dockerfile is a plain build + nginx (with `certs/` and SPA-fallback `nginx.conf`) and has no step that writes `window.__APP_CONFIG__`; the `BACKEND_URL`/`CLOUDFLARE_ENABLED` env vars in the release compose are not consumed by anything in the repo, so effective config comes from build-time `.env`/`.env.production` (`VITE_API_URL`, …).
- **Localization (i18n)**: `i18next` + `react-i18next`, languages `cs` (source of truth/fallback) and `en`; init in `src/i18n/index.ts` (imported in `main.tsx`). Translations are typed TS objects in `src/i18n/locales/<lng>/<namespace>.ts` (namespaces ≈ domains: `common`, `auth`, `courses`, `tasks`, `grades`, `attendances`, `student`, `admin`, `home`, `toast`, `errors`). `cs` defines the shape, `en` is typed as `typeof cs`, so a missing/extra key fails `tsc -b`. In components use `useTranslation('<ns>')` (use `['<ns>', 'common']` + `t('common:cancel')` for shared strings); outside components use `i18n.t` from `src/i18n`. Never concatenate translated fragments — use interpolation (`{{x}}`) or `<Trans>`. Format dates/numbers only through `src/i18n/format.ts` (`useFormatters`/`formatDate`…), never `toLocale*('cs-CZ')`. Toast and BE error texts live in the `toast`/`errors` namespaces (BE `errorKey` -> translation) and are resolved when the toast fires. Language is chosen by `LanguageSwitcher` (top menu), stored in `localStorage` (`app.lang`), default from the browser (cs/sk -> `cs`, else `en`). To add a language: add `locales/<lng>/*`, register it in `src/i18n/index.ts` (`resources`, `SUPPORTED_LANGUAGES`). Technical texts (logger output, the English-only admin client-log rule editor) are intentionally not translated.
- `src/model/*-dto.ts` mirror the backend DTOs; keep them in sync with `Models/Dtos`.
- Feature modals are grouped per domain in `src/components/<domain>/` with an `index.ts` barrel; shared state is in `src/contexts/` (Auth, Navigation, Attendance, StudentViewData).
